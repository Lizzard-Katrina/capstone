# 执行流程

请按以下顺序进行。每一步先说明你要做什么,再执行,再记录真实结果。

## 第一步:识别
- 查看仓库根目录和子目录,找出依赖文件(requirements.txt / setup.py /
  environment.yml / pyproject.toml)。依赖文件可能不在根目录,而在某个子目录里。
  记录你用的是哪一个,以及它的相对路径。
- 找出所有可能的入口脚本。**只考虑 .py 文件**,判据是:含 argparse,
  或含 `if __name__ == "__main__"`,或 README 里提到过的脚本。
  **全部列出,不要只挑一个**。
  **不要把 .cc / .cpp / .sh / .ipynb / Makefile 等非 Python 文件列为入口脚本** ——
  如果仓库主要由这些构成,在 verdict_reason 里说明,但 entry_scripts 只放 .py。
- 读取 README,提取其中给出的可执行命令。如果 README 没有具体命令(例如只写"详见论文"),
  记录为"无可提取命令",**不要自己编造**应该跑什么。
- 记录当前环境是否有 GPU(若已装 torch,用 torch.cuda.is_available() 检查;否则记为未知)。

## 第二步:安装依赖
- 按识别出的依赖文件原样安装,记录安装命令、退出码、日志末尾。
- 如果仓库完全没有依赖文件,记录 dependency_file_used 为 "none",跳过安装,继续下一步。
- 不论成功与否都进入下一步,不要因为安装失败就放弃整个诊断。

## 第三步:逐个测试入口脚本
- 对第一步识别出的**每一个** .py 入口脚本分别测试:
  用 argparse 的执行 `python 脚本路径 --help`;不像命令行脚本的则尝试 import 对应模块。
  **注意**:如果脚本在子目录里,记录时保持完整相对路径(例如 pythoncode/train.py),
  这样便于事后核对。
- 每个脚本单独记录结果,不要合并成一个笼统的"仓库通过/失败"。
- 若报错信息含 CUDA / GPU 相关内容,单独标记为 hardware_limited,不归入普通失败。

## 第四步:尝试 README 命令
- 对第一步提取到的每条命令限时运行(单条不超过 3 分钟);卡住就中断,记为 timeout。
- 若已产生正常输出(打印日志、开始读取数据)之后才因缺文件/缺模型权重报错,
  记为 data_boundary,**算作通过**。
- 若几乎没有任何输出就报错,记为 failed 并记录报错类型。
- 若第一步记录了"无可提取命令",这一步标记为 not_applicable,不要自己设计命令去跑。

## 第五步:给出总判定
- overall_verdict 取值:
  - `runs`: 依赖装上了,且至少一个入口脚本能正常启动(或 README 命令到达数据边界)
  - `broken`: 安装失败,或所有入口脚本都在启动阶段就报错
  - `undetermined`: 因硬件限制、超时或其他原因无法判断
- verdict_reason 用一句话说明依据,必须指向你实际观察到的现象。
